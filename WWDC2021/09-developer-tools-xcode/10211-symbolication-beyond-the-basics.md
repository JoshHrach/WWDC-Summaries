# Symbolication: Beyond the Basics
**WWDC21 · Session 10211** · [Watch](https://developer.apple.com/videos/play/wwdc2021/10211/)

_Platforms:_ iOS 15, iPadOS 15, macOS Monterey 12, watchOS 8, tvOS 15

## Overview
This session provides a deep technical foundation for understanding symbolication — the process of translating runtime memory addresses back into human-readable function names, file names, and line numbers. It explains why crash logs and Instruments traces are often only partially symbolicated and what developers can do to ensure maximum debug information is available.

The session covers the two-step symbolication process (going back to the file via ASLR slide calculation, then consulting debug information), three tiers of debug information (function starts, nlist symbol tables, and DWARF), and the Xcode build settings that control each tier. Command-line tools including `otool`, `nm`, `atos`, `symbols`, `vmmap`, `dwarfdump`, and `swift-demangle` are demonstrated throughout.

## Key Topics

### The Two-Step Symbolication Process
Step 1 — "Going back to the file": translates runtime addresses to on-disk file addresses by calculating the ASLR slide (ASLR slide = load address − linker address). The load address comes from the Binary Images list in crash logs or from `vmmap`; the linker address comes from `otool -l` examining `LC_SEGMENT_64` load commands.

Step 2 — "Consulting debug information": maps a file address to a function name, file name, and line number using one of three tiers of debug information.

### Function Starts (Lowest Tier)
Encoded in the `__LINKEDIT` segment and described by `LC_FUNCTION_STARTS`. Provides only the starting addresses of functions — no names. Allows offsets from function starts to be computed, useful for debuggers, but useless for human-readable crash logs. Inspected with `symbols -onlyFuncStartsData`.

### nlist Symbol Tables (Middle Tier)
Also in `__LINKEDIT` (`LC_SYMTAB`). Encodes `nlist_64` structs containing mangled names and addresses for direct symbols (functions involved in linking/export). Provides function names but not file names or line numbers. Inspected with `nm --defined-only --numeric-sort` piped to `swift-demangle`, or with the `symbols` tool. Local/static functions are absent; release builds typically strip the symbol table.

### DWARF Debug Information (Highest Tier)
Stored in `.dSYM` bundles (not in the app binary). Provides file names, line numbers, inline function information, and optimization records. Required for fully symbolicated crash logs and rich Instruments traces. Generated by the compiler and linker; controlled by Xcode build settings.

### Xcode Build Settings for Debug Information
- **Debug Information Format** (`DEBUG_INFORMATION_FORMAT`): `dwarf` embeds DWARF in the object files; `dwarf-with-dsym` generates a `.dSYM` bundle. Release builds should use `dwarf-with-dsym`.
- **Strip Linked Product** (`STRIP_INSTALLED_PRODUCT`): enables stripping during build.
- **Strip Style** (`STRIP_STYLE`): `all-symbols` removes most entries; `non-global` keeps exported symbols; `debugging-symbols` removes the nlist debug entries but preserves direct symbols.
- **Strip Swift Symbols** (`STRIP_SWIFT_SYMBOLS`): removes Swift-specific symbol table entries.

### dSYM UUID and Matching
Each dSYM has a UUID that must match the binary. The Xcode Organizer can download dSYMs for App Store builds. The `dwarfdump --uuid` command shows a binary's UUID. The `atos` command uses the binary (`-o`), load address (`-l`), and target address (`-i`) flags to produce fully symbolicated output.

## APIs & Frameworks

- `atos` command-line tool — symbolicate addresses; flags: `-o` (binary/dSYM), `-l` (load address), `-i` (inline)
- `otool -l` — print Mach-O load commands including `LC_SEGMENT_64`, `LC_FUNCTION_STARTS`, `LC_SYMTAB`
- `otool -tV` — print disassembly; `-arch` selects architecture for Universal 2 binaries
- `nm --defined-only --numeric-sort` — list defined nlist symbols in address order
- `swift-demangle` — demangle Swift mangled symbol names
- `symbols` — Apple tool to inspect function starts and nlist data; `-onlyFuncStartsData` flag
- `vmmap` — enumerate active runtime memory regions and load addresses
- `dwarfdump --uuid` — print UUID of binary or dSYM
- `Mach-O` binary format — `__TEXT`, `__DATA`, `__LINKEDIT` segments; load commands
- `nlist_64` struct — the C struct encoding symbol table entries; `n_type`, `N_SECT` bit pattern
- `LC_FUNCTION_STARTS` load command — points to function-start address list in `__LINKEDIT`
- `LC_SYMTAB` load command — points to symbol table in `__LINKEDIT`
- `dlsym()` / `dladdr()` — runtime dynamic symbol lookup powered by nlist symbol tables
- DWARF — industry-standard debug information format; file/line/inline data
- `.dSYM` bundle — container for DWARF debug information separate from the app binary
- `DEBUG_INFORMATION_FORMAT` Xcode build setting — `dwarf` vs `dwarf-with-dsym`
- `STRIP_INSTALLED_PRODUCT` — enables strip during build
- `STRIP_STYLE` — controls what is stripped: `all-symbols`, `non-global`, `debugging-symbols`
- `STRIP_SWIFT_SYMBOLS` — removes Swift-specific symbol entries
- Xcode Organizer — download dSYMs for App Store builds and re-symbolicate crash logs
- Instruments — uses dSYMs for rich trace symbolication

## Code Highlights

Computing ASLR slide manually:
```
ASLR slide = (load address from Binary Images) - (vmaddr from LC_SEGMENT_64)
File address = runtime address - ASLR slide
```

Using `atos` to symbolicate a single address:
```bash
atos -o MagicNumbers.app.dSYM/Contents/Resources/DWARF/MagicNumbers \
     -l 0x100045c000 \
     -i 0x1000461ab8
# Output: selectMagicNumber(choices:) (MagicNumbers.swift:12)
```

Inspecting load commands and disassembly:
```bash
otool -l MagicNumbers.app/MagicNumbers | grep -A 8 LC_SEGMENT_64
otool -tV -arch arm64 MagicNumbers.app/MagicNumbers
nm --defined-only --numeric-sort MagicNumbers | swift-demangle
```

## Takeaways

- Fully symbolicated crash logs and Instruments traces require a matching `.dSYM` bundle; always build with `dwarf-with-dsym` for release and archive builds.
- The ASLR slide bridges runtime addresses and on-disk addresses; every symbolication tool computes it automatically if you supply the load address.
- Symbol table stripping in release builds is normal and expected — it reduces binary size — but it does not affect dSYM-based symbolication.
- Understanding the three tiers (function starts → nlist symbols → DWARF) explains exactly why a backtrace may show offsets, function names without line numbers, or full source locations.
